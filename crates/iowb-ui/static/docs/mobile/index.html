Mobile clients are remote control surfaces for a running io-workbench server. They do not run your agent CLIs, workspace processes, or PTY locally. Start the host first, then connect the phone to a reachable authenticated server URL.

Choose the mobile surface

SurfaceBest forCurrent delivery
Android nativeA dedicated mobile experience with native editor and terminal controls.Signed APKs are published with every v* GitHub Release for arm64-v8a and x86_64. You can also build from source for development.
Web harness / PWAFast browser-based mobile use and the supported iOS path.Kotlin/JS responsive UI that can be served and installed as a PWA.
Legacy PWA fallbackSimple compatibility testing when the newer harness is not used.Package apps/mobile/www and host it over HTTPS.
iPhone / iPadSafari-installed web harness/PWA.The supported iOS route is the HTTPS browser/PWA surface. The SwiftUI shell is legacy/experimental; do not expect Android-native terminal, Database, or profile parity.

Prepare the server before installing a client

  • Finish host setup with Quick start and verify the selected project and provider CLIs on the server.
  • Choose a reachable address: a LAN IP on a trusted network, a VPN address, an authenticated tunnel, or an HTTPS reverse-proxy hostname.
  • Keep authentication enabled. Password, token, and OTP flows protect the remote client; a phone should not point at an unauthenticated public listener.
  • Forward WebSocket traffic as well as HTTP. Live events use /ws, so a proxy must support HTTPS and WSS end-to-end.
Never confuse a phone with the host

The phone may render a terminal or editor, but commands, files, Git operations, databases, provider CLIs, and the PTY still run on the connected server.

Install the native Android app

A release tag publishes signed APKs for the two supported Android architectures. On a physical phone, use the arm64-v8a release; use x86_64 only for a matching emulator. Read Install and update for the direct links, unknown-app-source permission, checksum guidance, and safe upgrade behavior.

  1. 1
    Pick the matching release APK

    Use io-workbench-android-arm64-v8a.apk from the latest release for a typical physical ARM phone, or io-workbench-android-x86_64.apk for an x86_64 emulator.

  2. 2
    Install it

    Download from the repository's GitHub Release page and use Android's installer, or with USB debugging enabled run adb install -r /path/to/release.apk. Android may ask to permit installs from the browser or Files app used for this one install.

  3. 3
    Launch the app

    The Android app stores server profiles, so one device can reconnect to more than one workbench host.

Build from source when developing the Android client

Install JDK 17, an Android SDK, and Gradle on PATH (or add a Gradle wrapper before using these commands). This repository does not include gradlew. Gradle detects the SDK through ANDROID_HOME, ANDROID_SDK_ROOT, or local.properties. The native Android project has a minimum SDK of 26 and produces ABI-specific debug APKs for arm64-v8a and x86_64.

Shell
cd apps/mobile
gradle mobileCheck
gradle :androidApp:assembleDebug -Piowb.android.enabled=true
find androidApp/build/outputs/apk/debug -name "*.apk" -print

Connect Android to the host

  1. 1
    Add server

    Start with Add server and optionally give the profile a name.

  2. 2
    Enter the API URL

    Use the exact base URL of the io-workbench host; omit a trailing slash when copying a public URL.

  3. 3
    Authenticate

    Enter username and password, a server token, or an OTP code according to the host authentication mode. The client probes /api/auth/status and follows setup, password, token, or open flow.

  4. 4
    Add headers only when required

    Use custom headers only when an authenticated proxy or access layer explicitly requires them.

  5. 5
    Connect and choose a project

    After the profile connects, select the remote project, open a session, and let the client reconnect its event stream when network conditions change.

Use the right URL for the device

Where the client runsUse this server URLWhy
Android emulatorhttp://10.0.2.2:8787The emulator's special host-machine address.
iPhone / iPad PWAhttps://workbench.exampleInstall the harness over HTTPS and use an HTTPS/WSS workbench endpoint. An HTTPS PWA cannot call an HTTP host without mixed-content blocking.
Physical device on trusted LANhttp://HOST_LAN_IP:8787Only when the host is intentionally listening on that LAN and the network is trusted.
Phone away from the hosthttps://workbench.exampleUse VPN, authenticated tunnel, or a reverse proxy that terminates TLS and passes WSS.

Use the PWA or browser harness

For the newer Kotlin/JS harness, install Gradle on PATH (or add a wrapper; this repository does not include gradlew), then run the browser development target or build a static distribution and serve it from a URL the phone can reach. The harness is the supported iPhone/iPad route; the older SwiftUI shell is experimental.

Shell
cd apps/mobile
gradle :webHarness:jsBrowserDevelopmentRun
# Or build a distribution:
gradle :webHarness:jsBrowserDevelopmentExecutableDistribution
cd webHarness/build/dist/js/developmentExecutable
python3 -m http.server 18880 --bind 0.0.0.0

Development server versus installed PWA

The Python server is appropriate for local development or a trusted LAN test. For a phone-installable PWA and service-worker behavior outside that path, serve the harness through HTTPS. An HTTPS-installed harness must connect to an HTTPS/WSS workbench endpoint, not http://HOST_LAN_IP, to avoid mixed-content blocking.

  1. 1
    Open the HTTPS harness

    On iPhone or iPad, open the harness URL in Safari. On Android, use the browser when you want the harness instead of the native app.

  2. 2
    Install it

    In Safari, use Share → Add to Home Screen. Other mobile browsers expose their own Install/Add to Home Screen action.

  3. 3
    Connect and authenticate

    Enter the HTTPS workbench base URL, then complete its supported login/register flow and select a project/session.

  4. 4
    Understand saved access

    The harness remembers one most-recent URL and credential/token in browser storage; it is not Android's selectable multi-profile store. Use a device lock and clear site data before handing a shared device to someone else.

PWA is an online control surface

The harness service worker caches the application shell, not /api/ data or /ws events. An installed PWA is not an offline copy of projects, chat, terminal, or database access.

Header-protected hosts

The native Android client can send custom access headers when a trusted proxy explicitly requires them. The web harness has no custom-header setup screen; use browser-level access or Android native for a hostname protected by service-token/header-only access layers.

For the legacy fallback, run cd apps/mobile && ./package-pwa.sh, host the unpacked www folder over HTTPS, then use the browser's Install or Add to Home Screen action. The legacy PWA connects with the API URL and bearer token; the newer harness can handle login/register flows.

Use mobile in a real work loop

Chat

Continue the remote session

Open or pin a session, send a bounded request, and inspect the same persisted response history you see on the web.

Files and Git

Review before approving

Read and save host files, then inspect Git status/diff on the remote project rather than assuming the agent summary is complete.

Database

Copy structured rows on Android

Native Android can select rows and copy/paste structured JSON or CSV. The browser database grid does not yet expose row clipboard controls.

Terminal

Control the host PTY

Android uses a native renderer built with Termux components and handy Esc, Tab, Ctrl, Alt, and arrow keys. Long-press the Terminal navigation button → Terminal renderer to switch between Native (Termux) and xterm rendering. It is not a local Termux/Linux environment.

First Android work cycle

  1. 1
    Connect the saved server profile

    Choose the profile you added, confirm its URL/auth state, and wait for the project list to load from the host.

  2. 2
    Open the project and Chat

    Select the remote project, open or create a session, choose the configured provider/model, and send a bounded request with a validation expectation.

  3. 3
    Review Files and Git

    Read the host files changed by the task, then inspect Git status/diff before you approve or continue the request.

  4. 4
    Validate in Terminal

    Open the remote PTY in the selected project and run the smallest relevant test, build, migration, or inspection command.

  5. 5
    Use Database on Android when needed

    Open Database → Explorer → Add connection, enter the connection, use Test, then Save. Use Explorer or SQL for a narrow check; select/copy/paste structured rows only after confirming the target.

  6. 6
    Record the result

    Return to Chat or Board with the diff, command result, and any data evidence so the next decision remains reviewable.

If connection fails

  • Wrong URL: test the address from the phone browser and confirm it points to io-workbench rather than a proxy login HTML page.
  • Network boundary: verify VPN/tunnel/proxy DNS, TLS, and WebSocket forwarding for /ws.
  • Authentication: confirm the selected password, token, or OTP mode and re-enter credentials after a server-side change.
  • Host service: check /health and the server process before rebuilding the app.
