A remote workbench should be operated as a persistent host service, not a browser tab or an expendable container. Preserve the server configuration/data and project workspace separately, put the listener behind the right network boundary, and prove each update before you rely on it.

Choose the persistent boundaries

BoundaryWhat to preserveWhy it matters
Configuration and server dataThe configured data directory and its server SQLite database.It contains workbench configuration, users, settings, session history, saved connections, and related state.
Project workspaceThe host directories you add as projects.Source files, Git repositories, database files, and Shell work remain here; they are not copied into a browser or phone.
Provider credentials and toolsThe host or custom image environment that runs Claude, Codex, and Gemini CLIs.The shipped container image does not install those CLIs or log them in for you.

Run a persistent container

The supplied image uses /data for configuration/data and /workspace for the workspace. Bind the host port locally when a reverse proxy, tunnel, or VPN will be the remote boundary.

Persistent Docker example
docker build -t io-workbench .
docker volume create iowb-data
docker run -d --name io-workbench --restart unless-stopped \
  -p 127.0.0.1:8787:8787 \
  -v iowb-data:/data \
  -v /srv/projects:/workspace \
  io-workbench

Treat the workspace mount as authority

Mount only the project root the server should control. A broad host bind mount grants the workbench, its authenticated users, agent CLIs, and Shell access to that data.

Persist provider login state deliberately

The /data and /workspace mounts do not by themselves preserve provider CLI authentication homes. Provision and persist the selected CLIs’ credentials for the same controlled container or service identity before relying on agent sessions.

Run a source build under a service manager

The repository includes deploy/io-workbench.service.example as a production baseline. Copy it to the host only after replacing the service user, data path, workspace path, and provider credential policy. Keep the managed binary outside a developer checkout so a deployment cannot overwrite local build output.

Release-binary systemd baseline
[Unit]
Description=io-workbench production host
After=network-online.target

[Service]
User=io-workbench
WorkingDirectory=/srv/projects
Environment=IO_WORKBENCH_HOST=127.0.0.1
Environment=IO_WORKBENCH_PORT=8100
Environment=IO_WORKBENCH_CONFIG_DIR=/var/lib/io-workbench
Environment=IO_WORKBENCH_WORKSPACE_ROOT=/srv/projects
ExecStart=/opt/io-workbench/io-workbench start
Restart=on-failure

[Install]
WantedBy=multi-user.target

Build the release binary with cargo build --release -p iowb-cli --bin io-workbench, or let the tag workflow replace /opt/io-workbench/io-workbench. Run the service as a dedicated non-login account where appropriate, and use Remote access rather than publishing a development listener directly.

Release-tag production deployment

Pushing a v* tag runs the release automation: it verifies the repository, publishes the checked native archives and Android APKs to GitHub Releases, then deploys the published Linux host package to workbench.giofahreza.com. The deployment job stages and verifies the release artifact before replacing the managed binary, restarts the configured service, and checks local plus public health.

StageWhat the automation provesOperator responsibility
ReleaseThe tag has published the platform packages, installers, APKs, and SHA256SUMS.Review the GitHub Release asset list and checksums before treating it as an approved production version.
Host updateThe configured Linux deployment host received the exact staged artifact and the service restarted.Keep service ownership, data directory, project workspace, provider CLIs, and credential material provisioned outside the replacement binary.
Public boundaryThe workflow polls https://workbench.giofahreza.com/health after the local health check.Keep the DNS/Cloudflare or reverse-proxy route, TLS, authentication, WebSocket forwarding, and firewall policy in place.
Public production health
curl -fsS https://workbench.giofahreza.com/health

Deployment prerequisites

The release workflow deliberately takes its SSH target, service name, installation paths, and health URLs from protected GitHub Actions secrets. Configure those once for the production host and limit the SSH key to the deployment account; a tag cannot safely invent a DNS route, service account, or provider credential.

Configure GitHub Actions and the production host once

The repository files deploy/README.md, deploy/io-workbench.service.example, and deploy/cloudflared-workbench-ingress.example.yml are the operator starting point. Use a dedicated release directory such as /opt/io-workbench; do not deploy over target/release in a source checkout.

Do not skip the one-time boundary work

Create the Cloudflare DNS/tunnel hostname, add the ingress route, reload cloudflared, give the deployment account narrowly scoped non-interactive permission to install the release binary and restart only this service, and store its controlled DEPLOY_SSH_KNOWN_HOSTS entry. The workflow never trusts a newly scanned SSH host key, and it intentionally fails its public health check until that boundary is real.

The release deployment replaces only executable code. It preserves the data/config directory and workspace, retains a timestamped prior binary, and automatically restores that prior binary if the new service fails local restart or health verification. If the public check still fails after a healthy local restart, use the workflow output to repair the tunnel/proxy boundary rather than deleting application data as an update workaround.

Back up, update, and verify

  1. 1
    Record the known-good state

    Capture the running version, configured paths, service/image version, and a health result before changing anything. Back up the configuration/data location and the relevant project repositories or database snapshots.

  2. 2
    Keep data while replacing code

    Stop only the service/container, replace the binary or image, and keep its configuration/data volume and workspace mount intact. Do not delete persistent data as part of an ordinary update.

  3. 3
    Restart and verify locally

    Start the updated instance and run curl http://127.0.0.1:8787/health. Then sign in, open one expected project, verify CLI Status, and perform a small Shell or session check.

  4. 4
    Verify the remote boundary

    If clients use a VPN, proxy, or tunnel, test HTTPS login and live WSS output after the local health check passes.

  5. 5
    Roll back deliberately

    If the new build fails, restore the previous binary/image and service configuration while preserving the data backup. Investigate schema/configuration compatibility before attempting a data rollback.

Inspect old workbench data without overwriting it

The legacy import is archival, not an automatic live-settings migration. It copies legacy files into a timestamped legacy-imports directory under the current config directory and leaves the original source unchanged.

Legacy archive import
cargo run -p iowb-cli --bin io-workbench -- import-legacy --dry-run
cargo run -p iowb-cli --bin io-workbench -- import-legacy

Review before relying on it

Run --dry-run first. Inspect the copied archive and decide what to migrate or recreate through the current UI; do not assume it restores active users, sessions, or settings automatically.
