Each version tag, such as v0.1.0, publishes the io-workbench host binary for Linux, macOS, and Windows plus signed Android client APKs. The host executable is the self-hosted server and Web UI; Android is an authenticated remote client. Install the package that matches the device you are preparing, then deliberately start or connect it.

Choose the right release asset

DeviceWhat the release installsWhat it does
LinuxA linux-x86_64 or linux-aarch64 host archive and the io-workbench/iowb commands.Runs the server, embedded Web UI, provider CLIs you have separately installed, projects, databases, and PTY on this machine. Both packages are built on an Ubuntu 22.04 glibc baseline for broad Linux compatibility.
macOSA macos-x86_64 (Intel) or macos-aarch64 (Apple Silicon) host archive.Runs the same local or remote host. It is a command-line host package, not a notarized Finder .app.
WindowsA windows-x86_64 ZIP with io-workbench.exe and iowb.exe.Runs the same host from PowerShell, Windows Terminal, a service manager, or another deliberate deployment boundary.
AndroidA signed android-arm64-v8a APK for physical ARM phones or android-x86_64 for a matching emulator.Connects to a running host. It does not run the host, provider CLIs, project files, databases, or a local Linux shell on the phone.

Linux and macOS: install the current host

Use this convenience command in a terminal. It resolves the latest GitHub Release, detects x86_64 or aarch64, downloads the matching archive, checks it against that release's SHA256SUMS, and installs the commands into ~/.local/bin. It does not use sudo and does not create or start a service.

Linux or macOS
curl -fsSL https://github.com/giofahreza/io-workbench/releases/latest/download/install.sh | sh

  1. 1
    Make the command visible

    Open a new terminal. If io-workbench is not found, add export PATH="$HOME/.local/bin:$PATH" to the shell startup file you use, then open a new terminal.

  2. 2
    Start the host deliberately

    Run io-workbench start. It listens on 127.0.0.1:8787 by default; open that local URL and complete first-user setup. Authentication stays enabled.

  3. 3
    Choose a remote boundary before sharing

    For another device, use the Remote access guide to put the host behind a trusted LAN, VPN, authenticated tunnel, or HTTPS/WSS proxy. Do not expose a development listener directly.

macOS security prompt

The release is a command-line archive, not a notarized desktop application bundle. Verify the release checksum and GitHub repository before running it; follow your organization's macOS policy if Gatekeeper asks for confirmation instead of broadly disabling Gatekeeper.

Windows: PowerShell installer or a downloaded script

Run the following in PowerShell to install the current x86_64 host package. The installer verifies the matching release checksum, installs into %LOCALAPPDATA%\Programs\io-workbench, adds that location to the current user's PATH when possible, and prints the next command. It does not start a host or register a service.

PowerShell
irm https://github.com/giofahreza/io-workbench/releases/latest/download/install.ps1 | iex

If you prefer to download and inspect the script instead of piping it into PowerShell, use the literal curl.exe flow below. Run it from a writable directory, inspect the file, then execute it with your normal PowerShell policy.

PowerShell with curl.exe
curl.exe -fL -o .\install-iowb.ps1 https://github.com/giofahreza/io-workbench/releases/latest/download/install.ps1
Get-Content .\install-iowb.ps1
.\install-iowb.ps1

  1. 1
    Open a fresh terminal

    PATH changes made for the user account are picked up by a new PowerShell or Windows Terminal window. If your policy blocks local script execution, inspect the downloaded file and use the approved execution-policy process rather than weakening system-wide policy.

  2. 2
    Start only when ready

    Run io-workbench start, then open http://127.0.0.1:8787. The default listener is local-only and the app's normal authentication flow remains enabled.

  3. 3
    Use a service manager for persistence

    A foreground terminal is suitable for a first local check. For a host that must survive sign-out or restart, follow Deployment and recovery and configure a deliberate service identity, data path, and remote boundary.

Android: install the released remote client

On a typical physical Android phone, open the ARM64 APK URL in the browser and install it with Android's package installer. The x86_64 APK is for a matching Android emulator; it is not the normal physical-phone choice.

Physical Android phone (arm64-v8a)
https://github.com/giofahreza/io-workbench/releases/latest/download/io-workbench-android-arm64-v8a.apk

Android emulator (x86_64)
https://github.com/giofahreza/io-workbench/releases/latest/download/io-workbench-android-x86_64.apk

  1. 1
    Download the matching APK

    Use the GitHub Release link in a device browser, or download it on a trusted computer and transfer it with USB/ADB. Use only the release asset for this repository and architecture.

  2. 2
    Allow that installer source

    Android may ask you to permit installs from the browser or Files app you used. Grant the permission only for that source, complete the installation prompt, and revoke it afterward if you do not normally sideload apps.

  3. 3
    Connect to a host

    Open the app, add the HTTPS/VPN/LAN base URL of an already-running io-workbench host, then authenticate and choose the remote project. The native terminal renders the host PTY; it is not a local Termux replacement.

Android is a client, not the server

Installing the APK does not install Claude, Codex, Gemini, Git credentials, a database server, project checkout, or host shell on the phone. Set those up on the Linux, macOS, or Windows machine that runs io-workbench start, then use the phone as its control surface.

Android does not include a universal curl command, but a computer with Android Platform Tools can download and install a repeatable APK over USB debugging. Replace the example tag and choose the matching ABI. The exact versioned names are io-workbench-vX.Y.Z-android-arm64-v8a.apk and io-workbench-vX.Y.Z-android-x86_64.apk.

Android phone from a computer with ADB
TAG=vX.Y.Z
ASSET=io-workbench-${TAG}-android-arm64-v8a.apk
curl -fL -o "$ASSET" "https://github.com/giofahreza/io-workbench/releases/download/${TAG}/${ASSET}"
adb install -r "$ASSET"

Verify a manual release download

The convenience installers verify their selected archive before installing it. When downloading an archive or APK yourself, fetch SHA256SUMS from the same release tag and compare the named asset before executing or installing it. Do not compare a checksum copied from a chat, screenshot, or a different release.

Linux checksum example
TAG=vX.Y.Z
ASSET=io-workbench-${TAG}-linux-x86_64.tar.gz
BASE=https://github.com/giofahreza/io-workbench/releases/download/${TAG}
curl -fLO "${BASE}/${ASSET}"
curl -fLO "${BASE}/SHA256SUMS"
grep " ${ASSET}$" SHA256SUMS | sha256sum --check -

Windows checksum value
$tag = "vX.Y.Z"
$asset = "io-workbench-$tag-windows-x86_64.zip"
$base = "https://github.com/giofahreza/io-workbench/releases/download/$tag"
curl.exe -fL -O "$base/$asset"
curl.exe -fL -O "$base/SHA256SUMS"
Get-FileHash ".\$asset" -Algorithm SHA256

What a release checksum proves

SHA256SUMS from the same GitHub Release catches corruption and selecting the wrong asset, but it shares the GitHub Release trust boundary and is not an independently signed authenticity proof. For release-build provenance, verify the downloaded file with GitHub CLI: gh attestation verify <downloaded-file> --repo giofahreza/io-workbench.

Windows comparison

Compare the hexadecimal value from Get-FileHash with the line for the same asset in SHA256SUMS. The release installer performs that exact asset-to-checksum check automatically; manual downloads require you to make the comparison.

Update and roll back deliberately

DeviceNormal updateIf something is wrong
Linux / macOSRun the same installer again, then stop/restart only the host process or service you intentionally manage.Keep the previous archive/binary and back up ~/.io-workbench plus projects before a production update. Use the deployment guide for a service rollback.
WindowsClose any running host process, rerun the installer, then start the new binary when ready.Keep data and project directories separate from the program directory. Restore the earlier verified archive only after stopping the managed process.
AndroidDownload the next APK for the same ABI and install it over the existing app. A release signed with the same key is treated as an update and preserves app data.If Android reports a signature mismatch, stop and verify that the APK is the official release asset; do not uninstall by default and lose local profiles before checking provenance.

Release security checklist

  • Prefer a version tag: use releases/latest/download only when you deliberately want the newest stable release; use a versioned asset such as v0.1.0 when you need a repeatable deployment.
  • Understand the convenience trade-off: curl | sh and irm | iex are fast paths. Download the installer first, inspect it, and run it locally when your security policy requires review.
  • Verify before execution: release installers verify native archives; compare SHA256SUMS yourself for any manual archive or APK install, and use gh attestation verify when you need GitHub build provenance.
  • Do not put credentials in installer commands: provider CLIs and their authentication remain on the host after the binary install. Keep credentials in that controlled host/service environment, never in a copied installer URL or mobile screenshot.
