Install io-workbench on the machine that owns your repository, provider CLI credentials, and development tools. The browser is the control surface; the host stays the place where code, processes, and agent CLIs run.

What runs where

Host

The source of truth

The Rust server, project directories, configured Claude/Codex/Gemini CLIs, Git credentials, databases, and PTY processes live on this machine.

Web UI

Your first cockpit

Open the local URL in a browser to sign in, choose a host project, start sessions, review files and Git, query data, and run a terminal.

Mobile

A remote client

Android and PWA clients call the same host over HTTP(S) and WebSocket. They do not run the agent CLI or terminal locally.

Before you start

  • Choose a release or source build: use a tagged prebuilt host when you want the supported Linux, macOS, or Windows executable; use source when you are developing io-workbench or need an unreleased change.
  • Current stable Rust and Cargo with edition-2024 support (Rust 1.85 or newer) are required only for a source install.
  • Git is required to clone the repository and to use workspace Git tools.
  • Submodule access: the root clone uses HTTPS but its current submodule URLs use GitHub SSH. Make sure an SSH key/agent can access GitHub, or rewrite the relevant submodule URLs to HTTPS and run git submodule sync --recursive && git submodule update --init --recursive if the recursive clone cannot fetch them.
  • A host project directory should be available under the workspace policy you intend to use.
  • Provider CLIs must be installed and authenticated on this host for each provider you plan to use. io-workbench supervises those CLIs; it does not install or authenticate them for you.

Install a released host binary

Release tags publish checked native host packages for Linux, macOS, and Windows. The one-line installer detects the operating system and CPU, verifies the release checksum, installs the command for the current user, and never starts a service on its own.

Linux or macOS
curl -fsSL https://github.com/giofahreza/io-workbench/releases/latest/download/install.sh | sh

For the Windows command, architecture choices, manual archive installs, Android APKs, checksum verification, and update procedure, use Install and update. After installation, start the local host deliberately with io-workbench start. Its default address is http://127.0.0.1:8787 and authentication remains enabled.

Install from source

For development or an unreleased build, clone recursively so the checkout includes its submodules, then start the server from the repository root.

Shell
git clone --recurse-submodules https://github.com/giofahreza/io-workbench.git
cd io-workbench
cargo run -p iowb-cli --bin io-workbench -- start

The default listener is 127.0.0.1:8787. It is deliberately local-only until you choose a remote-access boundary.

Open the web UI and create the first account

  1. 1
    Open the local address

    Visit http://127.0.0.1:8787 in a browser running on the host.

  2. 2
    Complete setup mode

    When no local user exists, the server presents first-user setup. Create the account that will own this local workbench.

  3. 3
    Keep authentication on

    Authentication is enabled by default. After setup, protected REST endpoints and WebSocket upgrades require your authenticated browser session or another supported credential.

  4. 4
    Add a host project

    In the sidebar, choose + Add project, browse to an existing host directory, and add it. That browser picker adds existing directories only. Create or Git-clone the directory through a trusted host workflow first, or use the separate native desktop or protected workspace-API flow when it fits your setup.

Default storage

Unless overridden, configuration is stored under ~/.io-workbench, the server database is ~/.io-workbench/io-workbench.db, and the workspace root starts at the host user home directory.

Verify the host before real work

Use the health endpoint to prove the running service is reachable. Use status separately to print the CLI's configured runtime information; it is not a substitute for a live health check.

Runtime health
curl http://127.0.0.1:8787/health

Configuration summary
cargo run -p iowb-cli --bin io-workbench -- status

  • Health should report that the server is reachable.
  • Status prints CLI configuration details; use it to inspect setup, not to prove a remote service is responding.
  • Settings → Agents → CLI Status is a readiness hint: it checks CLI version plus configured credential material. After it looks ready, prove the provider with one small, non-destructive agent task.
  • First project should open with its files and Git status visible before you rely on an agent session.

Optional: run in a container

A container is useful when you deliberately want the host runtime isolated. The repository, credentials, tools, and PTY still live in the host or container environment—not on a phone.

Shell
docker build -t io-workbench .
docker run --rm -p 127.0.0.1:8787:8787 -v iowb-data:/data -v "$PWD:/workspace" io-workbench

Provision provider CLIs in the image

The shipped image installs the base runtime tools, not Claude, Codex, or Gemini CLIs. Build a controlled custom image or otherwise provision the selected CLI and its credentials inside the container before expecting agent sessions to work.

For a persistent deployment, keep the configuration/data volume backed up, use a service manager or orchestrator rather than a foreground shell, and re-run the health check after an image or configuration update.

Continue with a real workflow

Use Install and update for release packages and device-specific installers, the web workspace guide for the first browser session, mobile apps for a phone client, native desktop client for the wxWidgets control surface, and Deployment and recovery before making the host persistent. If the server will be reached from another device, configure remote access before putting a public hostname into a client.
