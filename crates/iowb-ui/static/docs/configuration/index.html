io-workbench configuration uses environment variables with the IO_WORKBENCH_ prefix. Start from the safe local defaults, then make a focused change for storage, workspace scope, authentication, provider command behavior, or remote access.

IO_WORKBENCH_HOST127.0.0.1Keep first-run access local; change deliberately for a trusted LAN/proxy upstream.

IO_WORKBENCH_AUTH_REQUIREDtrueKeep authentication enabled; only disable for a deliberately trusted local dev setup.
IO_WORKBENCH_TOKENUnsetProvide token authentication for local automation or supported clients.
IO_WORKBENCH_OTP_SECRETUnsetEnable server-login TOTP with a valid Base32 secret.

Example: controlled local override

Shell
IO_WORKBENCH_WORKSPACE_ROOT=/srv/projects \
IO_WORKBENCH_CONFIG_DIR=/srv/io-workbench-config \
cargo run -p iowb-cli --bin io-workbench -- start

Restart after configuration changes

Environment variables are read by the server process. Apply the change in the service environment and restart the specific service instance that runs io-workbench.

Choose one server-login mode deliberately

With the default password mode, the first visitor completes single-user setup. Setting IO_WORKBENCH_TOKEN switches the server to token mode. Setting IO_WORKBENCH_OTP_SECRET switches it to TOTP mode; the secret must be valid Base32 and decode to at least 10 bytes.

  • OTP wins over token: when both variables are set, the server uses OTP mode rather than token mode.
  • Token or OTP always enforces authentication: either variable requires auth even when IO_WORKBENCH_AUTH_REQUIRED=false.
  • Token or OTP disables first-user registration: configure the chosen secret before exposing the server, then use the matching documented client flow. Native desktop has password/setup dialogs plus a bearer-token field, but no dedicated OTP field.
  • Do not confuse this with IO Gateway settings: Settings → IO Gateway has a separate optional Secret OTP for that integration. It does not configure io-workbench server-login TOTP.
Protect the secret

Store a token or TOTP secret in the service/container secret environment, not in browser/mobile code, chat history, screenshots, or a public shell profile.

Provider command configuration

The default commands are claude --print {prompt}, codex exec {prompt}, and gemini --prompt {prompt}. Use provider-specific variables such as IO_WORKBENCH_CODEX_COMMAND and IO_WORKBENCH_CODEX_ARGS_JSON, or global command/argument overrides, only when the host CLI truly requires them.

  • Argument templates support {prompt}, {session_id}, and {model}.
  • Stdin mode can be enabled with IO_WORKBENCH_AGENT_STDIN=true or a provider-specific variant when a CLI expects its prompt on stdin.
  • Validate first with CLI Status and one small agent task after changing command templates.

Limits and integrations

  • Runtime limits: configure maximum sessions, scan depth, file read size, tool timeout, and database transfer row limits using the documented IO_WORKBENCH_* variables.
  • Command-backed integrations: MCP, command, plugin, Taskmaster, push, and transcription variables point at host commands. Keep paths and arguments explicit.
  • Direct AI keys: provider-specific credentials such as ANTHROPIC_API_KEY or CODEX_GATEWAY_KEY belong in the server environment, not mobile/browser source.
